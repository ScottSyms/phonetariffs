# Cloudflare deployment

The public site runs on Cloudflare Workers with D1 for storage and static assets
for the UI. The DuckDB file remains the local source of truth; Cloudflare holds a
derived, disposable copy that CI rebuilds from source on every deploy.

```text
dfrp-rbif.xml ──┐
CNA CSV ────────┤
                ├─► python/build_database.py ─► phones.duckdb ─► export_cloudflare.py
                │                                                     │
                │                                        chunked SQL (dist/d1)
                │                                                     │
                ▼                                                     ▼
        (local CLI / PowerShell)                              wrangler d1 execute
                                                                      │
                                                                      ▼
                                       ┌──────────── D1 (phonetariffs) ───────────┐
                                       │  dfrp_* / telephone_* tables, FTS5 index │
                                       └────────────────────┬─────────────────────┘
                                                            │ env.DB
   browser ──► Workers static assets ──┐                    ▼
             └──► /api/* ──────────────► Worker (src/worker.ts) ──► JSON
```

## Contents

```text
cloudflare/
├── wrangler.jsonc             Worker name, D1 binding, static assets
├── migrations/                D1 schema migrations (applied by wrangler)
├── src/
│   ├── worker.ts              Router, validation, response shaping
│   ├── db.ts                  D1 queries, candidate retrieval, reranking
│   ├── fuzzy.ts               Scoring ported from python/phone_db.py
│   └── types.ts               Shared row/parameter types
├── public/                    index.html, app.js, style.css (no bundler)
├── scripts/seed-local.mjs     Loads dist/d1 data files into D1
├── test/                      Vitest tests (fuzzy + API, Workers pool)
└── worker-configuration.d.ts  Generated by `wrangler types`
```

## API

All endpoints are `GET`, return JSON, and allow cross-origin requests.

| Endpoint | Parameters | Cache |
| --- | --- | --- |
| `/api/meta` | — | 5 min |
| `/api/carriers` | — | 1 day |
| `/api/office` | `q` (required), `minimum_score` (0–1, default 0.35), `limit` (1–100, default 25) | 5 min |
| `/api/exchange` | same as `/api/office` | 5 min |
| `/api/property/:property_number` | path value, or `?number=` | 1 day |
| `/api/call` | `origin`, `destination` (required); `carrier_id`, `service_type` (default `standard_landline`), `date` (`YYYY-MM-DD`, default today) | 5 min |

```bash
BASE=https://phonetariffs.development-publishing.workers.dev

curl "$BASE/api/office?q=Port+Hopp&limit=5"
curl "$BASE/api/exchange?q=Ottawa"
curl "$BASE/api/property/31559"
curl "$BASE/api/call?origin=Toronto&destination=Ottawa&date=2026-06-01"
curl "$BASE/api/call?origin=Port+Hope&destination=Port+Hope"
```

### Search endpoints

Results mirror the Python CLI: every row plus `match_score`.

```json
{
  "query": "Port Hope",
  "table": "dfrp.property_search",
  "minimum_score": 0.35,
  "count": 2,
  "results": [
    {
      "property_number": "31559",
      "property_name_en": "PH35",
      "address_en": "330 Ward Street",
      "municipality_en": "Port Hope",
      "province_en": "Ontario",
      "match_score": 0.715
    }
  ],
  "note": "Fuzzy matches are candidate matches and require validation…"
}
```

Ranking uses the same formula as `phone_db.fuzzy_score`:

```text
score = 0.65 × token coverage + 0.35 × similarity
```

`similarity` is a bigram Dice coefficient rather than `difflib.SequenceMatcher`,
so scores differ slightly from the CLI and ties can order differently.

### Call evaluation

`carrier_id` is optional because tariff rules are carrier-specific: the same
route can be local under one carrier and long distance under another.

- **Omitted** — evaluates every carrier with a rule for the route and returns
  `by_carrier` summaries. `results` stays flat; group by `carrier_id` for display.
- **Provided** — filters to that carrier, exactly like the Python CLI.

```json
{
  "carrier_id": null,
  "origin_rate_centre": "Toronto",
  "destination_rate_centre": "Ottawa",
  "service_type": "standard_landline",
  "date": "2026-06-01",
  "count": 1,
  "status": "matched",
  "has_verified_rule": false,
  "by_carrier": [{ "carrier_id": "8051", "carrier_name": "Bell Canada", "count": 1 }],
  "results": [
    {
      "rule_id": "bell-on-toronto-ottawa-2026",
      "carrier_id": "8051",
      "carrier_name": "Bell Canada",
      "classification": "long_distance",
      "charge_applies": 1,
      "result": "charge_applies",
      "confidence": "derived",
      "effective_from": "2026-01-01",
      "source_document": "Bell Home Phone Basic Long Distance Rates",
      "source_url": "https://www.bell.ca/Home_phone/Long_distance_rates"
    }
  ],
  "note": "Only derived candidate rules matched…"
}
```

Interpretation rules the UI and API both follow:

| Field | Meaning |
| --- | --- |
| `status: "unknown"` | No rule matched. **Not** the same as free or chargeable. |
| `has_verified_rule: false` | Every match is `confidence: "derived"`. Treat as a starting point only. |
| `result` | `charge_applies` or `no_charge`, from `charge_applies`. |

### Errors

| Status | When |
| --- | --- |
| `400` | Missing `q`/`origin`/`destination`, out-of-range `limit`/`minimum_score`, malformed `date` |
| `404` | Unknown `/api/*` path |
| `405` | Method other than `GET`/`HEAD`/`OPTIONS` |
| `500` | Unexpected server error (details go to `wrangler tail`, not the response) |

## Data model

D1/SQLite has no user-defined schemas, so DuckDB's `dfrp.*` and `telephone.*`
namespaces are flattened:

| DuckDB | D1 |
| --- | --- |
| `dfrp.properties` | `dfrp_properties` |
| `dfrp.locations` | `dfrp_locations` |
| `dfrp.structures` | `dfrp_structures` |
| `telephone.co_codes` | `telephone_co_codes` |
| `telephone.carriers` | `telephone_carriers` |
| `telephone.exchange_assignments` | `telephone_exchange_assignments` |
| `telephone.calling_rules` | `telephone_calling_rules` |
| `telephone.tariff_sources` | `telephone_tariff_sources` |
| `dfrp.property_search` (view) | `property_search` (materialized) |
| `telephone.exchange_search` (view) | `exchange_search` (materialized) |

Types: `BOOLEAN` → `INTEGER` 0/1, `DATE`/`TIMESTAMP` → ISO `TEXT`, `DOUBLE` →
`REAL`. Dates compare as text, which is safe for ISO-8601.

The search tables carry `row_id` (integer key for FTS5) and `norm_text`
(accent-stripped, lowercased `search_text`, produced by `phone_db.normalize`).
Matching and scoring use `norm_text`, so accented input like `Montréal` matches
the same rows as the CLI.

`property_search_fts` and `exchange_search_fts` are external-content FTS5 tables
using the `trigram` tokenizer, which allows substring matching for terms of three
or more characters. Shorter queries fall back to a bounded `instr()` scan.

### Candidate retrieval

A Worker cannot load and score every row, so `src/db.ts` narrows first:

1. All-token and any-token FTS queries, each read twice — once ordered by bm25
   `rank`, once by `length(norm_text)` (a proxy for the similarity half of the
   score).
2. Deduplicate by `row_id` (up to 1,200 candidates).
3. Rerank with the exact scoring formula and keep the top `limit`.

Reading by length matters: for a one-word query like `Ottawa`, bm25 surfaces long
property descriptions and the short exact matches would fall outside the limit.

## Local development

```bash
mise install
mise exec -- python -m pip install -r python/requirements.txt

mise exec -- python python/build_database.py build
mise exec -- python python/export_cloudflare.py

cd cloudflare
npm ci
npm run db:local   # apply migrations + load dist/d1 into local D1
npm run dev        # http://127.0.0.1:8787
npm test
npm run typecheck
```

Local D1 state is keyed by the `database_id` in `wrangler.jsonc`. After changing
that ID, re-run `npm run db:local` or `wrangler dev` will report empty tables
(`no such table: …`).

`npm run db:local` is idempotent: the exporter emits `DELETE` + `INSERT`, so
reloading replaces data rather than duplicating it.

## Deployment

### Continuous deployment

`.github/workflows/deploy.yml` runs on every push to `main` that touches
non-Markdown files:

1. Checkout (Git LFS enabled — `dfrp-rbif.xml` is an LFS object).
2. `mise` install → Python and Node.
3. `build_database.py build` → `phones.duckdb`.
4. `export_cloudflare.py` → `dist/d1`.
5. `npm ci`, typecheck, tests.
6. `wrangler d1 migrations apply --remote`.
7. Load all 21 data files into remote D1.
8. `wrangler deploy`.
9. Smoke test `/api/meta` when `SITE_URL` is set.

Required repository configuration:

| Name | Kind | Purpose |
| --- | --- | --- |
| `CLOUDFLARE_API_TOKEN` | secret | Workers Scripts: Edit + D1: Edit |
| `CLOUDFLARE_ACCOUNT_ID` | secret | Target account |
| `SITE_URL` | variable | Enables the post-deploy smoke test |

Without `CLOUDFLARE_API_TOKEN` the `deploy` job is skipped with a notice, so the
workflow stays green until credentials are configured.

### Manual deployment

```bash
mise exec -- python python/export_cloudflare.py
cd cloudflare
npx wrangler d1 migrations apply phonetariffs --remote
node scripts/seed-local.mjs --remote
npx wrangler deploy
```

### One-time setup

```bash
npx wrangler login
cd cloudflare
npx wrangler d1 create phonetariffs
# Copy the returned database_id into wrangler.jsonc
npx wrangler d1 migrations apply phonetariffs --remote
node scripts/seed-local.mjs --remote
npx wrangler deploy
```

## Operating notes

- **Refresh CNA data**: `python python/build_database.py build --refresh-cna`,
  then re-export and reload. CI uses the committed CSV for determinism.
- **Add reviewed tariff rules**: `python python/build_database.py import-rules
  data/tariffs/calling_rules.csv`, then re-export and reload.
- **Schema changes**: add `migrations/0002_*.sql`, update the matching `TableSpec`
  in `python/export_cloudflare.py`, and confirm with
  `python python/export_cloudflare.py --verify-schema`.
- **Roll back code**: `npx wrangler rollback`. Data is reproducible from source,
  so a failed data load only needs the seed re-run.
- **Logs**: `npx wrangler tail phonetariffs`. Observability is enabled in
  `wrangler.jsonc`.
- **Regenerate types**: `npx wrangler types` after changing bindings, then commit
  `worker-configuration.d.ts`.

### Data reload behaviour

A deploy runs `DELETE` + re-`INSERT` per table, then rebuilds the FTS indexes.
The load takes a few seconds and is not atomic, so queries during a deploy can see
partially loaded data. The site stays available; only data freshness is affected.

### Limits and costs

- Dataset: 233,892 rows, ~55 MB of SQL across 21 files; D1 stores it comfortably
  within the free tier (5 GB).
- Free tier allows 5M row reads/day. Candidate retrieval caps work at ~1,200 rows
  per search; heavy traffic should add edge caching (Cache API) in the Worker.
- The exporter keeps every statement under 60 KB (D1's statement limit) and caps
  files at 4 MB.

## Known limitations

- **Fuzzy parity is approximate.** Same formula, different similarity function;
  scores are close but not identical to the CLI.
- **65 duplicated `rule_id` values** exist in the source data (exchange areas that
  slug to the same value under one carrier). D1 keeps them and therefore cannot
  enforce a primary key on `rule_id`; the exporter prints a warning each run.
- **Derived rules dominate.** Only the two Bell Toronto ↔ Ottawa-Hull reference
  rules are sourced; everything else is a same-exchange candidate, which is why
  `has_verified_rule` is usually `false`.
- **`dfrp-rbif.xml` is 129 MB in Git LFS**, pulled on every CI run and counted
  against GitHub's LFS bandwidth.
- **Carrier inference is not implemented.** The CNA data lists several carriers
  per exchange, so the UI offers "Any carrier" rather than guessing one.
